## 1. 结论

剩余工作主要有五块：

1. **代码证据完整流程**：从已完成的代码/配置校验内核，接到可实际使用的采集、校验、状态和交接操作。
2. **领域知识、严谨比较和图谱检索**：让论文与代码形成有类型、有条件、有证据的关联，能够判断实验是否可比，并检索支持和反对证据。
3. **完整文章与复现计划**：在已有提纲、章节和简单比较上，补齐跨论文综合、逐项支持检查、版本化产物和正式发布衔接。
4. **质量评测**：建立可复现的语料、问题、参考判定、模型运行和评分流程，找出真实使用中的遗漏与错误。
5. **产品整合与长期维护**：把分散的已有能力接成连续的使用流程，完成 Obsidian 阅读视图和覆盖新产物的备份恢复。

本计划将五块拆成 **12 个工作包，加 1 个最终集成验收包**。这是为了安排依赖与验收，
不是 13 个等量工时，也不代表需要重写已经完成的基础功能。

## 4. CODE：把基础校验接成可用的代码研究流程

### C1：文件读写、状态保存与异常恢复

**要做的开发**

- 在现有基础校验层之上实现 `code_proof_io.py` 和对应测试。
- 完成输入读取、保留文件/目录身份、大小与数量约束、锁、原子安装和重复操作复用。
- 覆盖读取中被替换、符号链接、内容改变、已占用输出、部分写入和清理失败。
- 保留原始证据与失败记录；中断后恢复不能跳过必须完成的校验。
- 对现有未采纳的生成产物仅作参考，按当前源码与合同重新核实，不能直接标为完成。

**已知缺陷必须转成回归案例**

- 安装失败后不能误报为可继续安装的 `idle` 状态。
- 最终校验中的一个分组失败时，不能跳过其他仍需执行的清理/身份校验分组。
- 关闭会话时释放保留的资源和描述符引用；异常读取旧状态不能绕过最终检查。
- 已保存资源缺失必须准确报错，不能被错误地忽略。
- 新安装和安装峰值预算检查仍需通过；输出已生成或源文件很长不表示完整交付。

**完成标准**

正常输入能得到确定且可复用的产物；相同请求重复执行不改变既有有效结果。
在关键阶段注入替换、冲突和中断后，系统返回准确错误或可恢复状态，
不会遗留看似完整但未经过校验的证据。此包完成后只证明 I/O 层可用。

### C2：公开操作、命令接线和实际交接

**要做的开发**

- 实现 `code_proof_public.py`，接入五类操作：`request`、`observe`、`status`、`config`、`handoff`。
- 将请求、观察结果、完整 commit、Git 对象、源码行和配置值的证据串联起来。
- 给未完成、部分完成、失败、冲突和可继续状态提供清楚的输出。
- 接入公开 CLI、安装包资源及连续流程测试；帮助信息能准确说明输入与结果。
- 输出供论文—代码关系和复现方案使用的交接材料，保留尚未证明的字段。

C2 内部按“公开状态与派生逻辑 → CLI 接线 → 安装包与全流程验收”推进。
现有 `code-map` 是不同的已有功能，不能把它当作新流程已经接通。
保留原始证据与规范化观察的区别；`status` 只读，不能在查询时偷偷修复文件；
`handoff` 要核对需要的完整目标集合。具体命令树和参数在实现前按现有合同明确。

**完成标准**

选择一个固定 commit 的示例仓库后，可以从请求走到代码/配置证据交接；
更换 commit、文件或配置会使不匹配的旧证据失效。网络观察由既有外部执行层提供，
Python 侧继续只消费记录。官方性和“真的能够训练”的判定不由代码 hash 自动得出，
相应关系与能力结论由 D1 的证据与审阅流程处理。

## 5. DOMAIN：把资料整理提升为严谨的研究比较

### D1：领域结构化知识与论文—代码关系

**要做的开发**

- 落地 Method、Model、ArchitectureComponent、TrainingRecipe、Dataset、Benchmark、InferenceRecipe、EvaluationMetric 八类概念。
- 将架构、训练、实验结果、实现、消融、局限、复现、许可、资源需求分别记录，避免全部混成普通摘要。
- 为领域标注、审核记录和当前版本增加兼容的存储、验证、编译和发布支持，保持已有 claim 身份与历史。
- 将论文、项目页、仓库声明、反向引用和作者控制证据连接起来，说明仓库与论文是本文实现、baseline、依赖还是第三方复现。
- 分别表达训练、推理、数据处理、评测和权重相关能力；“没有找到”必须附搜索范围。
- 对旧资料保留兼容读取或明确迁移步骤，不能改掉旧字段含义。

**完成标准**

同一论文的不同版本、不同实现与不同实验条件能够分别表示和追溯。
仅有相似账号名、README 引用或代码 hash 时，不自动判为官方实现。
修改当前标注不会删除历史结论；相关下游结果能检测到变化。

### D2：实验可比性、矛盾候选和比较矩阵

**要做的开发**

- 建立实验条件记录：模型/checkpoint、参数统计口径、数据及划分、指标及单位、分辨率、帧数、推理步骤、采样/指导配置和评测设置。
- 为每个值保存确切来源；未知值保持未知。
- 实现可比性检查，解释哪些差异允许比较、哪些会阻止直接比较。
- 输出支持、差异、疑似矛盾和信息缺口；先核对版本和实验条件，再提出矛盾候选。
- 在现有轻量比较模板之上生成结构化矩阵，并接入正式领域事实与版本变化检测。

**完成标准**

三篇论文可以产出逐格有来源的比较表。缺失关键条件或设置不一致时，
不会直接按数字排优劣，而会给出不可比原因和需要补齐的证据。
条件差异不会被误报成科学结论互相矛盾。

### D3：图谱投影和论文/代码联合检索

**要做的开发**

- 从正式记录重建类型化关系图，校验关系两端的类型和来源；不维护另一份独立事实真源。
- 接通论文、主张、方法、实验、代码和配置对象的查询及过滤。
- 将 exact、BM25 和图谱结果按排名融合，复用已有融合方法，不相加不同含义的原始分数。
- 上下文记录入选/省略项、排序理由、原文片段、支持/反对证据及预算。
- 将图谱、比较投影和现有目录的版本/覆盖状态一起检查；资料变化时不能继续冒充当前结果。

**完成标准**

同一个问题能同时返回相关论文解释、实验条件和代码/配置证据。
有相关反证时能够带入上下文；预算不足时显式说明未覆盖的争议。
相同输入和配置可重建相同投影与选择结果，来源过期或缺失时给出可执行的恢复动作。
历史回答和文章仍保留其原始版本引用；展示版本变化不会自动抹掉旧证据。
只有声明使用当前资料且相关依赖已经失效的结果，才按该状态阻止复用或要求重新检查。

## 6. SYNTHESIS：交付完整文章与可核查的复现方案

### S1：全文综合、修订与发布

**要做的开发**

- 复用已有提纲/章节修订，增加“研究问题→比较矩阵→文章结构→完整文章”的连续流程。
- 文章包含问题、共识、差异、争议、局限和未知项，而不只是拼接单篇摘要。
- 逐项检查事实、核心结论和表格单元的引用、版本、来源片段与支持情况。
- 补引用目录、文内引用和证据状态的一致性检查；更新来源后列出受影响的段落。
- 接通生成文章快照的准备、审阅、发布、替代关系、审计和备份；用户自己的笔记继续独立保存。

**完成标准**

同一研究主题能产出可阅读、可编辑的中文技术文章及比较表和参考文献。
每个关键结论能回到确切版本的原文或代码；修订生成新版本，旧版本仍可查。
草稿生成与正式发布有明确的实际状态，不能把写出 Markdown 就记成发布完成。

### S2：复现计划

**要做的开发**

- 将论文版本、对应仓库、完整 commit、入口、配置和所需权重版本连成一个计划。
- 列出软件环境、硬件、数据准备、许可条件、执行顺序、验证方法和预期输出。
- 对每一项标明有证据、推断、未知或阻塞，说明还需要取得什么资料。
- 检查论文描述、README、实际配置和代码之间的差异。
- 保存计划版本、来源和检查结果，接入检索、阅读视图与备份。

**完成标准**

用户能按计划判断是否具备复现条件，并定位到具体命令入口和配置。
缺训练代码、数据说明或必要参数时，计划明确停在哪一步及原因。
本项目交付的是可核查计划，不把未执行的训练或实验记为复现成功。

## 7. QUALITY：建立能发现真实问题的评测流程

### Q1：评测数据与执行工具

**要做的开发**

- 建立版本化的语料、问题、参考要点、证据、干扰项和评分规则。
- 分开开发集、正式验收集以及用于复测已知问题的回归集，保留各自用途。
- 记录来源/上下文/模型/提示词/配置/回答/审阅的确切版本与运行清单。
- 复用已有检索评估器，增加新证据单元指标和适用条件检查；旧 `evidence_recall_at_8` 保留原义。
- 增加回答支持度、必答要点覆盖、引用有效性、不可比判断、缺证据拒答和版本一致性的评分与报告。
- 完整保存失败、取消、替代运行和争议，不仅保留最好的一次结果。

**完成标准**

同一组固定数据能够重放评分；报告能区分召回不足、回答漏点、引用无效、
结论无支持和评测规模不足。评分工具通过测试不等于真实语义已经通过。

### Q2：真实论文、仓库与模型输出验证

**执行与修复顺序**

1. 先用原需求的 **3 篇真实论文 + 1 个确切对应仓库**，完成一次完整研究纵切，尽早暴露流程问题。
2. 覆盖中文检索、跨论文问答、实验不可比、版本切换、代码差异、长文引用和中断恢复。
3. 使用固定问题和实际独立生成结果运行评测，把问题转为有来源的回归案例。
4. 按实际适用条件扩充完整检索语料和真实仓库基线；小样本演示不替代完整验收。
5. 修复影响结果的排序、上下文选择、引用、比较和交互问题，再重跑受影响的整组案例。

**验收设计输入**

沿用最新 DOMAIN 评测准备文件，Q1 开工时将其固化为可执行规则：

- 基础问答至少 10 道可回答题和 3 道缺证据题。
- 比较至少 6 题，包含至少 2 道应判不可比的题。
- 完整 benchmark 至少 20 题，覆盖 model/method/training/dataset/inference/code。
- 完整 paper Recall@5 目标为 0.85，前提是声明的表示层至少有 30 篇合格、去重的候选论文。
- 新 evidence-unit Recall@10 目标为 0.75；每题需要真实干扰单元，且满足既定规模与审阅条件。
- 引用全部可解析，悬空引用为 0；回答事实需要支持，单题要点覆盖至少 80%、整体至少 90%。
- 对规定的模型验收样本执行 3 轮真实独立生成，保留每轮结果，不能复制缓存或只挑最好的一轮。
- 问答按三轮的最低表现判定，同时报告中位数、范围和失败明细；文章与复现方案保留核心结论全量审阅及其余内容的既定抽样范围。

具体干扰集、评分和语义审阅规则见
DOMAIN-ACCEPTANCE-PREPARATION-R2.md（`packets/full-todo-v1/DOMAIN-ACCEPTANCE-PREPARATION-R2.md`）
及 PRD 第 10 节（`video-generation-research-wiki-v1-prd-r3.3.md`）。
这些是待工具化并验证的目标，不是当前成绩。67 条 seed 题录不能充当 67 篇已处理全文。
真实科学结论的支持性需要实际审阅记录，不能由答案生成者自证。

## 8. PRODUCT：让分散模块形成连续使用体验

### P1：统一动作、状态和恢复

**要做的开发**

- 将预览、发现、选文、整理、问答、代码研究、比较、写作、状态和维护接入连续入口。
- 复用现有 read、ingest、query、preview、code-map、formal-source、audit 等 Skill 路由，补跨功能的意图分发；执行落到已有 CLI 和权威状态接口。
- 由已有的权威状态接口提供事实，统一显示正在进行、等待输入、需要审阅、来源过期和可以继续等用户可理解的状态。
- 为每一种失败或缺件给出明确下一动作，复用已有的局部恢复机制。
- 自动准备日常操作需要的结构化输入，减少用户手写 JSON 或在多套 CLI 之间搬运字段。
- 统一选择的论文/版本/研究会话在各步骤之间的传递，防止默认选中错误来源。

**完成标准**

用户能从“继续上次的研究”进入准确断点，并知道缺哪份材料或需要执行哪一步。
修改一篇论文后，只影响真正依赖它的内容；状态清楚且不丢笔记。
已有源码目录状态不再与轻量工作区状态混淆，也不建立新的重复状态真源。
增加“自然语言意图 → Skill/CLI → 实际状态/下一动作/所需输入”的验证矩阵，
既检查正确路由，也检查含糊选择、错误来源和已有阻塞时的行为。

### P2：Obsidian 阅读视图

**要做的开发**

- 复用 Paper/Code/Concept 页面，补领域字段、版本选择、比较表、文章和复现计划的阅读入口。
- 显示来源、审核/争议状态、更新影响和可导航的证据链接。
- 提供合适的索引页或 Bases 视图，支持按方法、任务、年份、基准和代码能力筛选。
- 检查中文排版、长表格、内部链接、图谱导航以及生成内容与用户笔记的所有权边界。

现有页面的阅读原型可在第二轮开始；包含比较、文章和复现计划的完整视图，
在对应产物实现后逐步接入并验收，不要求原型等待 S1 全部完成。

**完成标准**

从论文能走到实现、比较与文章，并返回原始依据；状态和版本可见。
重新生成页面不会覆盖用户自己的研究笔记。实际视觉效果需要在 Obsidian 中检查。

### P3：全部产物的备份与恢复

**要做的开发**

- 列清哪些内容不可重建：来源绑定、审阅/决策、研究会话、代码证据、比较记录、文章修订、复现计划和用户选择。
- 将新领域/文章/代码记录纳入已有的 manifest、完整性校验和恢复边界。
- 区分不可重建记录与可重建 catalog/graph 等投影；恢复后按正确版本重建并校验。
- 覆盖缺件、损坏、来源变化、旧版数据迁移和不同根目录的隔离恢复。
- 明确外部草稿和原 PDF 的保留位置及依赖，不能让不在归档内的材料看起来已被完整保护。

恢复清单要逐项覆盖：discovery 的观察、候选、会话和决定；workflow 断点；
library 维护日志；knowledge 的记录、batch、refresh；writing project 的提纲、章节和历史；
代码证据及正式来源/审阅记录；新增 Domain、Synthesis、Quality manifests 和运行记录。
已保存的观察、决定和历史结果按原字节保留；source catalog、文本索引、graph 等可重建投影
另列重建依赖和版本。不能只看到一个备份 ZIP 存在就认定这些状态全部已覆盖。

**完成标准**

在一个新目录恢复后，历史记录、研究断点与引用能继续使用；可重建部分经重建后一致。
缺失或损坏的材料被准确列出。已有轻量备份和正式 Vault 备份继续复用，重点是补齐整体覆盖。

## 9. 开发顺序与可并行工作

| 顺序 | 主线工作 | 可同时开展的独立工作 | 本轮结束时应展示什么 |

| 第一轮 | C1 → C2 | D1 的领域数据设计；Q1 的语料/评分接口；P1 的现有入口盘点 | 固定 commit 的代码与配置证据完整流程 |

这些轮次是依赖顺序，不是按天或周承诺的排期。

S1 的草稿可以提前，完整检索支持与正式发布仍需相关依赖完成。
共享 schema/registry、CLI 注册、发布和备份接口的修改需要串行集成，不能因并行而出现两套不一致的定义。

## 10. I1：最终集成验收

至少完整演示以下七条使用路径：

1. 预览/选择一篇论文，接收本地材料并整理成有定位的知识。
2. 通过已有发现流程扩展相关论文，保留候选、停止理由并能恢复。
3. 对固定版本的论文和仓库取得代码/配置证据，解释实现能力与未知项。
4. 回答跨论文问题，展示支持、反对证据和信息不足的情况。
5. 比较实验条件，输出有出处的矩阵并正确拒绝不公平的直接比较。
6. 形成完整技术文章和复现计划，修订后保留历史与来源。
7. 中断、修改来源、备份到新目录再恢复，继续研究并验证引用和视图。

每个工作包先完成适用的局部测试，再执行必要的整体回归、源码树外安装包检查及
Linux/macOS × Python 3.12/3.13 验证。测试数量不是产品完成度。
最终还要核对来源、发布、查询、文章、视图和备份在同一版本上的一致性。
